# Soulidity 生态标准化与并行重构输入

本轮施工前校准以[边界决策](open-ecosystem/CONSTRUCTION_BOUNDARY_DECISIONS_CN.md)为准：三类基线、B0、owned-only 构造、授权与收入生命周期、跨模块证明、暂停恢复、15 个保留维护单元、视觉及原产品分支已补充。原九表157条逐项见[范围追踪](open-ecosystem/ORIGINAL_SCOPE_TRACE.json)；精确函数／ABI／Cap 与运行验证仍需关口0及后续施工完成。[移交提示与材料](SOULIDITY_CONSTRUCTION_HANDOFF_CN.md)。

日期：2026-10-10。版本：1.1。阶段：Plan。用途：为现有重构提供明确的模块性质、接口、状态、权限、兼容、分工与验收边界。

**把项目拆成共同维护稳定标准的独立责任单元。模块可以单独重构、交付和替换，只有实际消费的业务契约变化才联动。** Maker、Soul 与第三方生产者独立；Soulidity、Animacraft 和各游戏是可替换的工具或应用。稳定标准提供格式与互操作基础，路由工具组合合法操作；资产本身的权利、供给和资金义务继续由实际入口执行。

首要验收是：新增独立被动外观／经历扩展后，旧市场的源码、依赖锁、配置和部署制品全部不变，原 Soul 仍能挂牌、取消、成交，市场被迫发布次数为 **0**。涉及资金、授权、供给、转移、托管、私密交接或退出限制的功能需要对应适配和证明，不能省略义务。

原设计阶段确定输入并同步文档。2026-10-10 用户已授权接管施工，并明确当前主线是按模块实际拆仓、细化管理功能与维护责任；本地拆仓和可逆源码重构已启动。GitHub／Slack 远端创建、提交／推送、生产部署及真实链上权限执行仍按各自明确授权办理。当前产品 Owner、DEV／BUG／Delivery、路线图和主仓 CURRENT 保留；实际施工进度记在重构工作树 CURRENT。建仓完成、模块解耦与原完整产品验收分别判断。

## 2 模块性质和责任归属

### 2.1 十个新增维护单元

| 模块／仓库 | 性质与维护核心 | 语义单元数及范围 | 权威状态 |
| --- | --- | --- | --- |
| STANDARD／soul-standard | 稳定资产标准 | 1：身份、来源、根与能力描述内核 | 自己的最小根状态；没有生态供给、服务费或订单 |
| CONTENT／soul-content | 可选内容与访问协议 | 3：引用托管、访问授权、内容恢复 | 实际内容引用、Blob 生命周期、策略与域内授权 |
| MAKER／maker-protocol | 独立资产及生产者协议 | 5：Maker 根、版本发布、发行适配、资产经济、Collection／Physical 关系 | 本资产版本、Draft、供给／资格、原权益及收入 |

| COMMUNITY／soul-community | 独立基础社区 | 1：基础社交 | 本实例作者内容、关系、分页与管理状态 |
| SDK／soul-sdk | 客户端工具 | 9：标准读取、根操作、Maker 发布、发行、内容、社区、市场、渠道、扩展适配 | 没有业务权威账本或钱包；恢复记录是证据索引 |

“最小模块”按能独立维护的规则和权威状态划分。不要把一个内部函数拆一个仓库，也不要为达到数量而新建重复发行器、账本或万能适配层。Model／Visual 等同仓语义单元可以独立构建与发布；如果真实包共用升级边界，明确登记这种联动。后续独立维护／发布需求成立时再拆仓，Channel／Market 已按用户要求现在分开。

| --- | --- | --- |

| F04 | 扩展操作 | 精确域、动作、根证明、代次、期限、限额、CAS；不能越域修改 |

| F06 | 资格供给发行 | 真正贡献资产、Pack／版本、资格、计数维度和原子发行；生产者实际权威 |
| F07 | 内容生命周期 | 精确字节摘要、Blob／托管、认证、用途、期限、续期权限与实际恢复 |
| F08 | 访问操作授权 | 主体、对象／域、动作、网络／实例、版本／代次／期限；实际域内写点校验 |
| F09 | 渠道协议 | 条款、资产版本、主体动作、币种／金额／受益人／额度／时效、不可重放的行为结果 |
| F10 | 订单原子结算 | 原订单／资产／双方、报价承诺、分配、精确 policy 实例／代次、适配、终态与真实交付 |
| F11 | 收入资产政策 | 原权益、规则、账本、真实权利人、币种精度／舍入与领取；服务收入归本实例 |
| F12 | 应用结果 | 实际应用与规则、输入能力、结果来源、范围、防重放；本地模拟不自证有效经历 |
| F13 | 社区 | 作者、实例、父子关系、内容引用、revision／分页；管理无资产权 |
| F14 | 意图恢复 | 固定输入／字节／digest、原结果与检查点、已付资源、下一合法步骤 |
| F15 | 组合交付证据 | 源码／差异／锁／哈希、工具、网络／包／类型／对象／配置、消费者和恢复证据 |
| F16 | 服务治理与包生命周期 | 实际实例／包、动作、真实权限与全部控制路径、预期状态、退出、旧入口和迁移；各域实现，无生态总治理合约 |

接口族不是 16 个新合约包，也不是已冻结函数签名。具体 ABI 必须可跨真实包编译，不能把 `public(package)`、私有 witness 或同包类型搬开后当作现成公开接口。

每个实际消费者在本仓 `MODULE.md`／`COMPATIBILITY.md` 声明 **8 项**：提供方与精确接口、实际使用动作／类型、支持的 schema／行为范围、必要效果、真实权限／状态输入、失败与退出／恢复、版本组合与制品身份、验证与迁移证据。没有使用的能力不自动成为依赖。外部开发者复用同一公开标准和参考实现，不必接受平台推荐目录的审批。

### 3.2 七种依赖分别登记

| 依赖种类 | 例子 | 变化的处理 |
| --- | --- | --- |
| 编译 | Move 类型来源、公开签名、SDK import | 固定依赖闭包；不可兼容时适配或迁移 |
| 运行 | 选用市场实例、Blob 读取设施、实际解密服务器 | 可替换设施与不可替换状态分开；实例替换不隐式继承权利 |
| 行为 | ABI 不变但校验、舍入或退出规则改变 | 消费相关行为者必须重新验证，必要时适配 |
| 权限 | Control、授予代次、根路径、升级包装 | 验证所有有效直接与间接控制路径 |
| 资金 | 费率、币种、原权益、收入分配 | 原规则与逐币种对账；没有遗漏／半完成 |
| 状态 | revision、schema、唯一 counter、迁移进度 | CAS、旧 writer、并发和历史保护 |
| 内容 | 精确资源、认证、有效期、访问政策 | 本操作必要资源及实际恢复条件；未选资源不阻断 |

每条依赖边记录 **8 项**：消费者、提供方、种类、所用动作／类型／状态、选用条件、精确版本范围、变化触发的验证、退出／迁移。编译成功只证明部分兼容；链上字段能读也不证明授权和资金结果安全。

### 3.3 目标依赖方向

- Standard 不反向依赖 Maker、Native、Channel、Market、Community、Vault 或平台 Config。
- Maker 根／发布核心不强制依赖 Soul；需要 Soul 的发行／增强是 Maker 选用的适配。Native 或第三方生产者直接调用 Standard，拥有自己的真实发行规则。
- Market 订单内核依赖所支持资产的最小身份／合法转移契约；不固定导入所有应用、Vault、Content 或 Channel。资产维护者提供必要政策／交接适配，市场维护组合桥。
- Channel 协议核心不固定绑定 Market 或唯一生产者；选中资产的行为适配才依赖其具体规则。渠道额度不能复制资产总供给。
- 扩展只调用 Standard 和自己选用的内容／来源／权限契约。不同扩展不互持万能写权。
- Community 独立维护基础社交。SDK 按所选子包导入；DevOps 与 Integration 没有业务运行门控权。

这张方向图是目标语义边界，实际导入图由后续准确候选生成。目录拆开之后仍有反向业务依赖、同包私有 ABI 或统一 Config 的，不算完成解耦。

## 4 扩展性质与市场互操作

### 4.1 六类效果和四种操作能力

每项能力分别标明能否 **read、write、carry、handover**，并列出 **6 类效果**：资金／权益、授权／私密交接、供给／资格、转移／托管、内容可用性、退出／历史。一个扩展可能有多个效果；没有填报不是没有义务。描述绑定准确类型／对象与行为版本，实际效果仍由真实写入口和证明执行。

| 性质 | 默认行为 | 消费者处理 |
| --- | --- | --- |
| 被动外观／经历数据 | 独立 namespace、自有状态，不增加消费者必须执行的义务 | 旧市场携带原资产；未知展示可降级，不迫使市场发布 |
| 主动可写能力 | 选定应用按范围写入；使用实际根证明／CAS／代次 | 只影响用该写契约的消费者，其他游戏与市场独立 |
| 带资金／授权／交接义务 | 真实政策和效果证明不可跳过 | 消费该义务的路径必须适配或明确拒绝 |
| 带转移／锁定约束 | 约束必须落在实际能够阻止违规的转移路径 | 只能承诺已验证路径的限制；未知容器／路径不能冒称支持 |
| 内容与退出条件 | 实际认证、期限、密钥和必要状态保留 | 不删除必要来源、余额、Bound、历史或存量权益 |

**旧市场无法预知未来任意限制。** 对有 `store` 且允许自由 `public_transfer` 的类型，单加“锁定／租赁／抽成”字段不能保证所有外部路径被拦截；能力目录也不能变成通用钩子。希望强制义务的生产者必须设计真实受约束接口／policy／持有路径，验证既有入口与容器是否可绕过，并给出合法出口。无法做到的范围明确说明；不把它计为符合跨市场强制政策的资产。

原生 Kiosk 路径与 Market 自有订单托管分别适配。`TransferPolicy<Soul>` 这个类型存在不证明调用了指定 policy 实例、代次和规则；逐项核实允许路径与退出。A→B→A 不能仅凭当前 owner 地址证明旧 grant 永久失效。未知第三方扩展的交接结果不从已知应用的清理函数推导。

### 4.2 市场内核、资产适配与组合桥

| 层 | 维护者 | 必须维护的结果 |
| --- | --- | --- |
| 订单内核 | MARKET | 报价与有效交付关系、订单 CAS／终态、收款／分配、取消、服务收入与重放防护 |
| 资产语义适配 | 实际资产／政策／扩展维护者 | 真实来源、三类权利、资格、费用、授权／Vault／其他交接效果和合法转移路径 |
| 组合桥 | MARKET／CHANNEL 对应组合维护者 | 显式连接已选择的协议、资产结果与完成证明；不新增全生态总路由权限 |

一次成交中的付款、政策、权利、供给消耗与资产交付必须原子完成；独立维护不拆散一次交易。目标机制可用类型化且不可伪造的线性证明／完成票据和显式 PTB 组合，具体 ABI 与防绕过须编译和攻击路径验证。可持久保存的普通收据不能替代不可丢弃的完成条件。不要假设 Sui 有任意动态模块回调。

PTB 的原子性与 Move abilities 由实际代码证明；失败交易 gas 独立计入，不能说失败完全没有成本。[Sui PTB 官方说明](https://docs.sui.io/develop/transactions/ptbs/prog-txn-blocks)

## 5 渠道协议、订单与存量义务

渠道默认非独家，授权限制在精确资产／版本／行为／期限／额度。接受条款不等于付款或占用总供给；网页导流与公开读取不自动构成抽成依据。合法未选路径执行原资产政策，但无该渠道费用。已接受且实际消耗的受限代理能力不能通过“直接调用”绕过对应义务。

| 所处情况 | 撤销／到期／控制交接时的选定策略 |
| --- | --- |
| 未接受 | 不执行渠道业务、不收费、不占额度 |
| 已接受，尚无订单或实际预留 | 停止新的代理行为；不会形成追溯收费或额外供给 |
| 仅有报价／挂牌 | 不视为已付承诺；停止新的受撤销授权结算，保留合法撤单／重新选择路径；不能消费旧代理能力伪装直连 |
| 真实有效预留 | 若现有模型存在预留，按原绑定条款／期限履约或取消释放；不追溯修改费率、受益人或虚构预留。最终钱与发行仍原子 |
| 已履约 | 原收据、权益、收入与计数保留；不能撤销后再交付或重复记账 |
| 执行未知 | 先查原 digest 及权威状态，再决定是否能取消、释放额度或新尝试 |

原协议进入 ENDED 后不能用原 ID 复活；重新同意用新协议身份／代次。市场订单状态由 Market 单独维护，渠道 ACTIVE／ENDED 不代替订单终态。Maker／内容／渠道／交易的原状态域继续分开，不新增生态总状态机。

换客户端可以接续原实例；换 Channel 或 Market 实例属于不同选择。新实例不得隐式继承旧余额、Cap、订单、授权、额度或收入。需要迁移时，由真实权利和原状态机提供明确迁移步骤及证据，不靠一次“同步”假定完成。

## 6 权限与自动执行

每个仓库登记源码维护、版本发布、生产部署、链上控制 **4 类工程边界**，合计 40 项适用性记录；无链上状态的工具仓注明不适用。链上权限按真实对象和状态评估，不按五个业务入口或十仓机械发几把 Cap。

| 权力 | 推荐边界与不得遗漏的有效路径 |
| --- | --- |
| 配置 | 本实例新业务参数；若可改受益人、提款条件或资金政策，登记真实间接资金权 |
| 资金 | 本账本、本币种、真实收入权利人；不混用户／创作者／其他服务余额 |
| 暂停 | 本实例明确新风险动作；逐条验证撤单、收入与资产出口，不能只测暂停按钮 |
| 升级 | 实际包／UpgradeCap／策略及全部可绕过路径；共包即共升级边界，升级改变规则的权力也要披露 |
| 授权／支出 | 实际根／容器证明与域内 grant；内容读取、应用写入不等于 Vault 支出。通用资产支出代理继续后置 |

配置、资金、暂停、升级应能分别识别和控制。同一主体持有多项时明确披露；同一 Cap 实际涵盖多个权力时据实登记并评审拆分，不虚构隔离。多签、延迟、升级限制、永久不可升级、资产锁和紧急暂停各自验证，不凭“管理员已分开”认定风险消失。

Sui 升级后旧包不会自动消失，依赖不自动跟随，结构／签名兼容也不能证明行为相同。有效版本守卫、旧入口、依赖重绑定和迁移必须验证。[Sui 包升级官方说明](https://docs.sui.io/develop/publish-upgrade-packages/upgrade)

自动授权与维护采用公开条件、真实写点验证和受约束执行者，不绑定 Soulidity。执行者只能在目标对象、动作、预算／期限／受益人等限制内提交；持有对象或规则不会自行发起交易。无需平台业务服务器不代表没有 RPC、Walrus 网络、实际认证与私密解密设施。

## 7 变更、验证与发布规则

### 7.1 四类变化，区别验证与发布

| 类别 | 判定与例子 | 行动和量化要求 |
| --- | --- | --- |
| 独立变化 | 新被动 namespace、某游戏自己的 UI、未选 SDK 子包 | 发布自身；消费者四类基线不变，被迫发布 0 |
| 所用契约兼容变化 | 原签名下增加正确处理或优化，已用接口行为仍在承诺范围 | 重跑受影响组合；结果满足原契约时消费者可保持固定制品 |
| 所用契约不兼容变化 | 必需 schema、付款／授权／转移效果、实际 policy、币种精度变化 | 消费者适配或拒绝；精确记录受影响范围，不能省略义务 |
| 类型／状态不兼容迁移 | 真实类型来源、旧对象结构、供给或账本迁移 | 对应基线原权利／ID／历史与唯一权威保护，具体迁移另证；逐阶段恢复、旧入口和合法出口证明 |

变更记录检查 **4 个维度**：类型／格式／ABI、业务行为、权限／资金、状态迁移／旧入口。版本号或签名未变不能省略后三项。新增模块不默认扩大所有消费者的依赖。

### 7.2 选择验证闭包

1. 模块维护者声明变更的接口、状态、效果和实例，以及上述七类依赖。
2. Integration 按消费者的八项声明计算受影响闭包；共享计数、policy 或 root writer 必须沿真实规则扩展验证。
3. 绑定相关 CASE、原 T 组与原卡；每个模块在本地／CI 检查自己，跨仓验证准确组合。
4. 至少验证基线／当前、候选／当前、候选／候选 **3 种版本组合**；有反向消费再加反向组合。错误哈希和不兼容组合拒绝。
5. **重新验证不是重新发布。** 合同继续成立的消费者固定源码、依赖、配置和制品；只有适配或真实迁移才要求消费者发布。

各仓 CI 均通过不能替代组合通过；某组合失败不默认冻结所有无关模块。结果按准确组合阻断和恢复。发布清单不得使用浮动 latest、未声明全局 Config 或从平台 API 取得唯一参数。

编译依赖、schema 和语义演进分开：若旧 Market 实际写入共享 application schema，给 character 加一个“可选字段”仍可能让旧 writer 不兼容。应迁出独立 capability 或适配真正受影响契约；不能简单声称“都是 Soul 所以市场不变”。

## 8 制作、内容与中间状态

制作工具公开工程与快照格式；每个在途发布固定工程 revision、素材／许可、规则／源版本、必要内容、精确摘要与已生成随机密文。继续编辑产生下一候选，不替换已付意图。Maker 根已创建不等于版本 READY；渠道接受不等于已经发行。

保留 **5 个状态域、24 个状态码、38 条转移**：制作、内容、版本发布、渠道、单步交易。最终 Soul 发行的线性 Build 必须单 PTB 完成；Maker 多交易发布可以有可恢复检查点。业务终态与单步执行终态分别记录。

恢复优先级：原意图／原 digest→原 effects 与历史对象→已成功资源／检查点→当前状态和下一合法动作。EXECUTED_SUCCESS 后读回失败保持原成功，不降 UNKNOWN；签名过期不单独证明未执行。换客户端携带可公开恢复信息与安全备份，绝不导出私钥或把密钥写到公开链上。

Walrus 的期限、Blob 权限、认证和续期资金按真实对象核实；并非永久无成本。私密内容在上传前加密，Seal 等需要实际密钥服务和可恢复政策；旧密钥不是换 URL 就一定能恢复，撤销不能收回已保存明文。公开路径不强制选私密子系统。[Walrus 生命周期](https://docs.wal.app/docs/walrus-client/managing-blobs)、[Sui Seal](https://docs.sui.io/sui-stack/seal)

社区关系、分页和基础发现由公开链上结构支持，避免必须全链扫描或平台私有数据库。推荐排序、复杂运营和体验优化可在具体客户端演进；这些变化不控制资产合法操作。干净环境接替保留真实公共设施或可验证替代，不以关闭整条 Sui／Walrus 网络作为测试条件。

## 9 分工、并行与 DevOps

十模块沿用总说明的角色建议：SDK／Content 由 LUQI、DevOps 由 HARBOR、Integration 由 FLUX 与 IRIS、合约域由 CIPHER 统筹及原 Owner，Community 客户端由 SABLE。实际独立验收者负责验收；SENTINEL 角色名称不能代替资金／权限审查资格。原 Owner 不变。每个完整旅程仍有一个现有集成责任人。

建议试运行最多 **2 个隔离实现槽＋1 个只读验证槽＋1 个协调槽**；这只是执行容量上限，不能把原全局 **1 条主要旅程＋1 条基础设施** WIP 自动改成十条。一个原旅程内可并行准备不同模块子项，但必须满足依赖和验收容量。每个已开工模块最多一个实现任务／写入者。

并行开工须同时满足 **6 个条件**：范围已授权、原 WIP 可容纳、工作树／写域隔离、输入契约固定、独立审查容量已预留、无独占资源冲突。Agent 的 MODULE／AGENTS 指定唯一可写单元；不能因“帮忙修集成”直接改别人的权威源码。

共享 schema、原 Config、唯一计数、同一 root revision 的变更，按实际冲突串行或 CAS 设计；钱包／浏览器操作、相同部署环境和同一签名资源设唯一持有者、获取与释放条件。工作树只隔离文件，不隔离这些外部状态。

| 协作项 | 实施目标与退出条件 |
| --- | --- |
| GitHub／Slack | 新增 10 仓／10 模块频道；先查重；每个有链接、Owner 和可访问维护入口 |
| 表单／视图 | 3 类共用表单，字段 5／7／7；10 模块视图＋1 跨模块视图，不复制任务库 |
