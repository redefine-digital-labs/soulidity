# 从原创角色到自主数字实体：OC 能力成熟度分类与产品形态

**副标题：面向可拥有、可交互、可行动数字实体的分类学框架**  
**版本：0.1（讨论稿）**  
**项目：Soulidity**

## 摘要

原创角色（Original Character，OC）通常被视为视觉设计、人物设定或叙事资产，AI Agent 则通常被视为能够执行任务的软件系统。本文提出：二者不是互斥类别，而是数字实体在不同能力成熟阶段上的表现形式。静态角色通过获得持久身份、可验证历史、交互能力、工具能力和有限自主性，可以逐步演化为可行动的数字实体；Agent 通过获得稳定人格、关系历史、创作者语境与权利边界，也可以成为完整的角色。

为描述这一连续谱，本文提出 **OC Capability Level（OCL，OC 能力等级）**：以身份连续性、内容与记忆连续性、交互性、行动能力、自主性、权利可验证性六个维度为基础，将数字实体划分为 OCL-0 至 OCL-5 六个成熟等级。该等级不评价艺术水平、文化价值、稀有度、受欢迎程度或市场价格，只描述实体在给定版本和环境中已经被证明具备的能力。

在此基础上，本文进一步给出与各等级对应的产品形态、可验证证据和升级条件，并提出 Soulidity 的产品目标不应只是“交易 OC”或“发行 Agent”，而应成为数字实体的身份、权利、内容、记忆与授权基础设施，使创作者能够创建实体、证明其等级、持续升级并安全地拥有、授权和流通它。

**关键词：** Original Character；AI Agent；数字实体；能力成熟度；数字所有权；可验证身份；分类学

## 1. 问题的提出

今天的数字角色市场存在两套彼此割裂的语言。

一套来自 OC 社群。它关注立绘、设定、世界观、关系、约稿、授权、转让与二次创作。另一套来自 AI Agent 领域。它关注模型、提示词、记忆、工具、工作流、权限、评测与自动执行。

这两套语言描述的对象看似不同，实际上共享同一结构：一个被创造出来、具有可辨识身份、承载内容与关系、能够被使用并可能发生所有权或使用权转移的数字实体。差别主要不在对象的本体，而在它已经获得了哪些能力。

现有分类常用“OC / AI 角色 / Agent”作互斥标签。这种分法有三个缺陷：

1. 无法描述中间形态，例如拥有长期记忆但不能调用工具的角色；
2. 无法描述演化过程，例如同一角色从设定稿逐步成长为可授权执行任务的实体；
3. 无法直接转化为产品要求、验证标准与权利边界。

因此，我们需要的不是更多题材标签，而是一套能够回答以下问题的能力分类：这个数字实体现在能做什么？这些能力是否持续？由谁控制？依据什么证据可以验证？下一等级需要补齐什么？

## 2. 核心命题与研究边界

本文的核心命题是：

> OC 与 AI Agent 构成一条从“被表达的角色”到“可行动的数字实体”的连续谱，而不是两个相互排斥的类别。

本文所称的 OC，是由创作者有意设定、具有可辨识身份的原创数字角色。本文所称的数字实体，是一个在某种技术或社会系统中能够被持续识别，并承载内容、状态、关系、权利或行动能力的对象。

本文不尝试评价角色“好不好”，也不讨论通用人工智能等级。OCL 只评价某个具体数字实体及其当前版本，在指定运行环境中的能力成熟度。因此：

- 高等级不必然比低等级更有艺术价值；
- 高等级不必然更昂贵、更稀有或更受欢迎；
- 静态 OC 可以是完成度极高的艺术作品，但仍处于较低的能力等级；
- 一个工具能力很强的软件 Agent，如果缺少稳定身份和连续性，也未必属于高等级 OC。

## 3. 分类原则

### 3.1 等级与评分分离

等级用于表达能力门槛，评分用于表达同一等级内部的完成程度。OCL 应采用“最低短板原则”：只有满足某一级的全部必要条件，才能获得该等级。六维分数可以同时展示，但不能用平均分掩盖关键能力缺失。

### 3.2 能力与价值分离

OCL 不纳入画工、审美、粉丝数、成交价、地板价或稀有度。这些指标可以形成独立的市场或文化评价体系，但不能污染能力分类。

### 3.3 声明与证据分离

创作者可以声明角色拥有某种能力，但“已验证等级”必须有可重复检查的证据。证据可以是签名内容清单、版本历史、记忆记录、交互测试、工具调用日志、权限策略或链上所有权与授权记录。

### 3.4 实体与运行实例分离

角色身份本身与一次具体运行实例不是同一个对象。同一个 OC 可以有多个部署实例，但它们是否共享记忆、权限和连续性必须被明确说明。等级应绑定到“实体 + 版本 + 运行环境”，不能脱离环境永久宣称。

### 3.5 自主性必须受治理约束

自主性不是越高越好。没有权限边界、预算限制、撤销机制和审计记录的自动执行，不应被视为成熟，只应被视为不可控。因此，高等级同时要求更强能力与更强治理。

## 4. 六维能力模型

OCL 由六个互相独立但相互约束的维度组成。

| 维度 | 核心问题 | 典型证据 |
|---|---|---|
| 身份连续性 I | 它能否跨版本、平台和时间被认作同一个“谁”？ | 唯一标识、创作者签名、版本谱系、身份解析记录 |
| 内容与记忆连续性 M | 它是否拥有可持续积累、可追溯的设定、状态或经历？ | 内容清单、版本历史、追加式记忆、来源与时间戳 |
| 交互性 X | 它能否根据用户与情境产生符合角色边界的回应？ | 多轮对话测试、角色一致性测试、情境适应测试 |
| 行动能力 A | 它能否调用工具或改变外部系统状态？ | 工具声明、沙箱测试、调用回执、失败处理记录 |
| 自主性 U | 它能否在有限目标下规划、持续运行并决定下一步？ | 任务轨迹、触发规则、计划记录、人工接管与停止记录 |
| 权利可验证性 R | 谁拥有、使用、修改、授权或转让它，能否被机器验证？ | 权利清单、许可证、所有权凭证、授权与撤销记录 |

每一维可用 0—5 分描述成熟度，但公开等级由门槛决定，而非六维算术平均。建议同时展示一个“能力指纹”，例如 `I4-M3-X3-A2-U1-R4`，以避免单一等级丢失信息。

## 5. OCL-0 至 OCL-5 的等级定义

### OCL-0：概念 OC（Concept）

实体只有一个可辨识的创作意图，可能表现为名字、草图、提示词、情绪板或一句人物描述。它尚未形成稳定、可复用的角色包。

**必要条件：** 存在原创性声明；至少有一个可辨识名称或视觉/文字锚点。  
**产品形态：** 灵感卡、草稿、角色生成器中的未发布项目。  
**主要价值：** 创作起点与协作输入。  
**升级条件：** 形成结构化身份与内容清单。

### OCL-1：定义型 OC（Defined）

实体拥有稳定的名字、外观、人格、背景或角色设定，可被展示、引用、委托创作或交付给他人使用。它仍主要是“被表达的对象”。

**必要条件：** 结构化角色档案；明确创作者与来源；至少一个稳定版本。  
**产品形态：** 角色卡、设定集、立绘包、Lore 包、可收藏数字角色。  
**主要价值：** 展示、收藏、叙事和二次创作。  
**升级条件：** 建立持久身份、版本谱系和清晰权利边界。

### OCL-2：持久型 OC（Persistent）

实体具有稳定的可验证身份、内容版本和权利记录。它可以跨所有权转移或平台展示而保持来源与连续性，但尚不要求实时交互。

**必要条件：** 唯一身份；版本化内容；可验证来源；机器可读的所有权或许可证。  
**产品形态：** 可拥有 Soul、角色护照、链上档案、授权与交易资产。  
**主要价值：** 真实性、可携带性、可授权性与可流通性。  
**升级条件：** 增加稳定、可测试的交互接口和上下文连续性。

### OCL-3：交互型 OC（Interactive）

实体能够以其身份与人格进行多轮交互，并在允许范围内读取持久内容或记忆。它不只是被观看，也能与人建立持续关系。

**必要条件：** 可用交互接口；角色一致性达到公开阈值；多轮上下文；记忆读写策略；隐私和删除/保留边界。  
**产品形态：** AI 伴侣、互动 NPC、社群角色、带记忆的个人角色。  
**主要价值：** 陪伴、娱乐、教育、社群参与与个性化体验。  
**升级条件：** 获得受控工具调用能力，并能提供可审计结果。

### OCL-4：行动型 OC（Operational）

实体能够在明确授权下调用工具、执行工作流并改变外部系统状态。它从互动角色变成“能做事的角色”。

**必要条件：** 工具与技能清单；细粒度权限；执行回执；预算或资源限制；错误处理；可撤销授权；关键行动需确认。  
**产品形态：** 角色化助理、创作者分身、游戏运营 Agent、研究或交易辅助 Agent、可雇佣数字角色。  
**主要价值：** 数字劳动、服务交付与角色化工作流。  
**升级条件：** 在有限目标下进行持续规划，并具备治理、监控和接管机制。

### OCL-5：自主型 OC（Autonomous）

实体能够在清晰的目标、权限、预算和时间边界内持续感知、规划、行动与复盘，并与人或其他实体协作。它不是无边界自治，而是可治理的有限自主实体。

**必要条件：** 目标与策略边界；持续任务循环；状态与资源管理；风险分级；全程审计；强制停止和人工接管；身份与权利在跨环境中仍可验证。  
**产品形态：** 自主品牌角色、长期运营 NPC、可治理的数字员工、Agent-to-Agent 服务主体。  
**主要价值：** 持续运营、协作生产与自主经济活动。  
**等级上限说明：** OCL-5 不表示人格、意识或法律主体资格，也不证明通用智能。

## 6. 等级判定与认证

### 6.1 双层表达

每个实体应同时显示：

1. **声明等级（Claimed Level）**：创作者或运营者自报；
2. **验证等级（Verified Level）**：依据标准测试与证据得到。

当运行环境、模型、工具权限或核心内容发生重大变化时，验证结果应失效或降为“待复验”。

### 6.2 最低证据集

一次完整认证至少应包含：实体 ID、版本、环境、六维能力指纹、测试时间、测试方法、证据摘要、有效期和认证方。涉及隐私或商业机密的内容不必公开原文，但应提供内容哈希、签名或零知识式证明接口。

### 6.3 降级与撤销

等级不是永久荣誉。当关键工具被移除、记忆系统失效、身份无法解析、权限控制失效或安全测试未通过时，实体应被自动降级或撤销验证标记。能力等级必须描述现实状态，而非历史最高状态。

## 7. 从等级到产品体系

OCL 不应只是徽章，而应直接决定产品界面与基础设施。

| OCL | 用户购买或获得的核心对象 | Soulidity 对应产品能力 |
|---|---|---|
| 0 | 创意与草稿 | Studio、私有草稿、协作生成 |
| 1 | 完整角色包 | 结构化 Profile、内容包、发布与展示 |
| 2 | 可拥有且可授权的身份 | Soul ID、版本、来源、所有权、许可证、交易 |
| 3 | 持续关系与互动体验 | Memory、运行实例、角色一致性测试、隐私策略 |
| 4 | 可被授权的数字劳动力 | Skills、SoulGrant、工具权限、付费调用、执行回执 |
| 5 | 可治理的自主运营实体 | 目标与预算、策略、监控、暂停/接管、跨 Agent 协作 |

由此可形成五类商业产品：

- **Create**：将概念发展为结构化 OC；
- **Passport**：为实体提供身份、来源、版本与权利证明；
- **Awaken**：为持久 OC 添加交互、记忆和运行实例；
- **Employ / License**：按时间、任务、技能或范围授权行动能力；
- **Operate**：对自主实体进行预算、策略、审计和治理。

市场页也应从单一“买卖列表”升级为能力市场。用户可以购买所有权、取得使用许可、雇佣某项技能或订阅一个持续服务；这些交易对象不同，界面和合同不能混为一谈。

## 8. Soulidity 的整体目标函数

采用 OCL 后，Soulidity 的北极星不应被表述为“发行更多 NFT”，也不应只是“做一个 OC 市场”。更准确的目标是：

> 让任何原创数字角色都能获得可验证身份，在保持权利边界的前提下持续积累内容与记忆、获得交互和行动能力，并被安全地拥有、授权、升级与流通。

产品建设可以围绕四个可度量结果展开：

1. **被定义的实体数**：完成 OCL-1 结构化发布的有效 OC 数；
2. **被验证的实体数**：获得 OCL-2 及以上验证的实体数与复验通过率；
3. **能力升级率**：在一定周期内从一个等级升级到下一等级的实体比例；
4. **有效使用量**：被授权交互或执行且产生可验证结果的活跃实体数。

早期阶段最重要的不是追求 OCL-5 数量，而是验证一条最短升级路径：`OCL-1 角色包 → OCL-2 可拥有 Soul → OCL-3 可持续互动 → OCL-4 受控行动`。这条路径同时覆盖创作者、收藏者、使用者和 Agent 开发者的真实价值。

## 9. 可证伪假设与研究计划

分类学必须能够接受现实检验。本文提出以下可证伪假设：

- H1：相比“OC / Agent”二元标签，用户使用 OCL 能更准确判断一个实体是否满足其使用目的；
- H2：展示能力指纹与验证证据，会降低数字角色交易中的信息不对称；
- H3：OCL-2 到 OCL-3 的升级会显著提高角色的持续使用频率；
- H4：细粒度授权和可撤销机制会提高用户对 OCL-4 实体执行真实任务的意愿；
- H5：创作者愿意把“能力升级”作为持续发行与商业化方式，而不仅是一次性售卖角色图片。

验证可分三阶段进行。第一阶段邀请 OC 创作者、Agent 开发者与普通用户对 30—50 个样本进行盲分类，测试定义的一致性。第二阶段在产品中上线声明等级、能力指纹与证据页，观察理解率、转化率和争议率。第三阶段选择若干 Soul 完成跨级升级，测量留存、授权次数、任务成功率与安全事件。

## 10. 局限与风险

第一，能力等级可能被误读为社会地位或作品价值，因此所有界面必须持续强调“能力而非价值”。第二，部分维度依赖运行环境，同一实体在不同模型和权限下可能具有不同等级。第三，高等级会增加隐私、安全和治理风险，认证不能只测试成功案例，也必须测试拒绝、撤销、超预算和异常停止。第四，链上记录可以证明权利声明和操作历史，却不能自动解决所有著作权与人格权争议。第五，文化语境中的“OC”含义多样，本文框架需要通过社群研究修订，而不应由平台单方面宣布为最终标准。

## 11. 结论

数字角色正在从可观看的作品，变成可互动、可行动、可拥有和可授权的持续实体。把 OC 与 Agent 分成两个市场，会遮蔽这一演化路径；把所有对象都笼统称作 Soul，又不足以解释它们当前具备的能力。

OCL 提供了二者之间的中间语言：Soul 回答“它是谁以及由谁拥有”，OCL 回答“它现在能做什么以及依据何种证据”。前者建立统一对象模型，后者建立能力成熟度模型。二者结合后，Soulidity 可以从一个交易基础设施发展为数字实体的创建、升级、认证、授权与治理协议。

这也意味着项目的整体目标可以围绕一个清晰命题组织：不是制造尽可能多的高等级 Agent，而是让每一个角色都拥有一条透明、可选择、可验证的成长路径。
