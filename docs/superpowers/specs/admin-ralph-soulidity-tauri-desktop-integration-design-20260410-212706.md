## Problem Statement

LLM CLI tools (Claude Code, Cursor, Aider) are terminal-native and invisible. Users interact with AI all day but have no visual representation of the AI's state. Meanwhile, the Soulidity marketplace has paying customers who customize Souls heavily, spending more time on personalization than expected. The desktop companion bridges these two worlds: a persistent visual layer that turns on-chain Souls into ambient, reactive companions tied to the user's real coding workflow.

## Demand Evidence

- Paying customers already exist in the Soulidity ecosystem
- Users customize Souls heavily — more time on customization/collection than expected, indicating emotional ownership, not just utility value
- This customization behavior signals that Souls have identity-projection value that a desktop companion would amplify from "thing I visit on a website" to "thing that's always with me"

## Status Quo

Current LLM CLI users see: a terminal. Text in, text out. No visual feedback beyond streaming tokens. Some CLI tools show spinners or progress bars. The gap between "I'm working with an AI partner all day" and "I see nothing" is total.

Current Soul owners interact with Souls through the web marketplace only. There's no persistent touchpoint. The emotional ownership exists but is confined to browser sessions.

Desktop pet alternatives (AI Desk Pet on Steam, tama96, BongoCat) exist but are disconnected from the user's actual AI workflow and have no marketplace or ownership layer.

## Target User & Narrowest Wedge

**Target user:** Existing Soul marketplace customer who uses LLM CLI tools daily for coding. Already demonstrated willingness to pay for Souls and invest time customizing them.

**Narrowest wedge (Phase 1 — Approach A):** Desktop avatar that reacts to LLM CLI state. Four states: idle, thinking, generating, error. 2D sprite/Lottie animation. Single CLI source (Claude Code). Transparent overlay window. Reuses existing persona download/install system. No minting, no agent wallet, no voice. Ships in 2-3 weeks.

**Evolution target (Phase 2 — Approach C):** Agent-first companion where the Soul has its own Sui wallet, monitors CLI activity, and has LLM-powered opinions and reactions. The visual layer becomes the face of an autonomous agent.

## Constraints

1. Must extend the existing Tauri v2 desktop app (not a new project)
2. Must reuse existing persona download/install/activate system
3. Must integrate with existing Soul marketplace and catalog API
4. Transparent overlay window must be always-on-top without stealing focus
5. CLI monitoring must be non-invasive (read-only observation, not injection)
6. Soulidity design system applies (dark Web3 aesthetic, purple/teal/gold color coding)
7. macOS first (existing Tauri target), Windows follow

## Premises

1. LLM CLI users want a visual companion layer on their desktop (defended against Codex challenge — founder believes in broader audience, not just existing Soul buyers)
2. Monitoring LLM CLI state (thinking/generating/idle/error) provides enough behavioral variation to keep the avatar interesting daily
3. Existing Soul marketplace customization behavior will transfer to desktop companion context
4. On-chain ownership (Souls as NFTs) creates retention that pure desktop pets lack
5. The emotional bond with the avatar is tool-agnostic — users keep their Soul companion even when switching CLIs
6. Tauri desktop app is the right delivery vehicle (vs. menu bar app, browser extension, or terminal-native)

## Cross-Model Perspective

Codex steelmanned the product as "an emotional operating system for AI-native workflows" — not a desktop pet, but a ownable, customizable, portable emotional layer. The key insight: "what you're really selling is identity projection + emotional ownership, not CLI state visualization."

Codex challenged Premise #1, arguing most CLI users would view a desktop avatar as distraction. Proposed validation: 20 heavy CLI users, 3 days, measure "continuous 6+ hour" retention rate. If <25% keep it running or >50% disable the avatar on day 1, the premise fails. If users keep the menu bar icon but close the avatar, they want observability, not a companion.

Codex's 48-hour prototype: Reuse Tauri v2, React+Zustand frontend, Rust sidecar for CLI event monitoring (one source: Claude Code or generic JSONL watcher), 2D sprite/APNG/Lottie (no Live2D), four states, local progression tracking (companion hours, tasks completed, streak). Skip everything else.

Founder defended Premise #1 for the broader audience. The Codex validation test (6-hour continuous use) remains the key metric regardless.

## Approaches Considered

### Approach A: Sprite Companion (Minimal Viable) — SELECTED FOR PHASE 1
- Transparent overlay window with 2D sprite/Lottie avatar, four states
- Rust sidecar watches one CLI source (Claude Code stdout/JSONL)
- Reuses existing persona download system
- System tray icon for quick settings
- No Live2D, no 3D, no minting, no agent wallet, no voice
- Effort: M (2-3 weeks) | Risk: Low
- Pros: Ships fast, validates core hypothesis, reuses existing auth + persona download pipeline (~30-40% of Phase 1 scope)
- Cons: Visually simple, single CLI source, may feel too basic. Overlay window, CLI monitor, sprite engine, and system tray are new code.

### Approach B: Rich Companion (Ideal Architecture)
- Live2D/Spine animation engine, multi-CLI monitoring, voice/TTS, Soul minting, configurable LLM keys, own Sui address
- Effort: XL (8-12 weeks) | Risk: High
- Pros: Full vision, maximum wow factor
- Cons: 3 months before user contact, high risk of building unused features

### Approach C: Agent-First Companion — SELECTED FOR PHASE 2
- Soul IS an agent with its own Sui wallet
- Monitors CLI activity AND has LLM-powered opinions (comments on code, reacts emotionally)
- Visual layer is secondary to agent behavior
- Effort: L (5-7 weeks) | Risk: Medium-High
- Pros: Differentiates from every desktop pet, agent identity is the moat, creates utility reason to keep it open
- Cons: LLM cost per user, agent behavior needs careful tuning

## Recommended Approach

**A then C.** Ship the Sprite Companion (Approach A) in 2-3 weeks to validate the core retention hypothesis: will users keep the companion running all day? Measure 6-hour continuous use rate. If retention holds, evolve toward Agent-First Companion (Approach C) where the Soul gains a brain and a wallet.

## Phase 0: CLI Observability Spike (2-3 days, BLOCKING)

**目标:** 验证两个最高风险依赖，通过则进 Phase 1，失败则降级为 tray-only MVP。

### US-P0-002: CLI 进程检测 POC (Rust)

**验收:** Rust 模块能检测 Claude Code 进程是否在运行，每 200ms 轮询一次，状态变化通过 Tauri event 发送到前端。

**文件变更:**
| 文件 | 变更 |
|------|------|
| `desktop/src-tauri/src/cli_monitor.rs` | 新建模块：`CliState` enum (Idle/Active/Error)、`start_cli_monitor()` 启动 tokio task、`sysctl` 或 `ps` 进程检测、`app.emit("cli-state-changed", state)` |
| `desktop/src-tauri/src/lib.rs` | `mod cli_monitor;` + 在 `run()` 中启动 monitor task + 注册为 managed state |
| `desktop/src/companion/Overlay.tsx` | 监听 `cli-state-changed` 事件，显示当前状态文字（验证事件通路） |

**探索方向:**
1. `sysctl kern.proc.all` 或 `Command::new("pgrep").arg("-f").arg("claude")` 检测进程
2. 测量 3 个终端模拟器（Terminal.app、iTerm2、VS Code Terminal）下的检测可靠性
3. 记录检测延迟（从 Claude Code 启动到 monitor 首次检测到的时间）

**验证清单:**
- [ ] Claude Code 运行时 overlay 显示 "Active"
- [ ] Claude Code 未运行时 overlay 显示 "Idle"
- [ ] 状态切换延迟 <500ms
- [ ] 在 Terminal.app / iTerm2 / VS Code 终端下均可检测
- [ ] CPU 开销 <1%（Activity Monitor 验证）

### US-P0-003: CLI 日志/输出 tailing POC (可选)

**前置:** US-P0-002 完成后，如果进程检测只能区分 idle/active，尝试日志 tailing 获取更细粒度状态。

**探索方向:**
1. Claude Code 的 `~/.claude/` 目录是否有日志文件或 JSONL 事件流
2. 如果有：用 `notify` crate (kqueue) 监听文件变化，解析最近事件判断 thinking/generating/error
3. 如果没有：记录结论，Phase 1 用 2 态（idle/active）代替 4 态，UI 合并 thinking+generating 为 "working"

**验证清单:**
- [ ] 确认 Claude Code 是否输出可观察日志
- [ ] 如果有日志：能区分 thinking vs generating vs error
- [ ] 记录每种信号的延迟和可靠性

### US-P1-004: Sprite Sheet 渲染引擎

**验收:** Avatar.tsx 能加载 sprite sheet 图片，按当前 CLI 状态播放对应动画帧序列。

**技术实现:**
```
Sprite Sheet 格式契约:
├── {persona}/companion/idle.png       # 水平排列帧，如 8 帧 x 100px = 800px 宽
├── {persona}/companion/thinking.png
├── {persona}/companion/generating.png
├── {persona}/companion/error.png
└── {persona}/companion/manifest.json  # { frameWidth, frameHeight, frameCount, fps } per state
```

- CSS `background-image` + `background-position` + `animation: steps(N)` 实现帧动画
- 每个状态独立的 sprite sheet 文件，manifest.json 声明帧参数
- `prefers-reduced-motion`: 只显示第一帧，不播放动画

**测试:**
- `tests/desktop/companion-avatar.test.tsx`: mock sprite manifest → 验证正确帧数 / CSS animation 属性

**Overlay Window:**
- Tauri transparent, always-on-top window (separate from the management window)
- Click-through behavior: the overlay passes all mouse events to windows below, EXCEPT a small drag handle region (top-center, 40px wide bar with grip dots). Right-click on the drag handle opens the context menu (show/hide, switch Soul, settings). All other mouse events pass through to the window below
- Frameless, draggable via handle, resizable via context menu
- Sits in corner of screen (user-configurable position, persisted across restarts)
- Background: **fully transparent** (no visible container). The Tauri window is transparent with no chrome. The avatar floats directly on the desktop like BongoCat/WindowPet. This means the window background is `transparent`, not a card.
- No border, no box-shadow on the window itself. Individual floating UI elements (speech bubble, status bar) carry their own subtle backgrounds.
- Drag target: the avatar sprite itself is the drag target (not a visible handle bar). Cursor changes to grab on hover over the avatar area.

**Overlay Size Presets:**
| Preset | Window Size | Avatar Area | Use Case |
|--------|-----------|-------------|----------|
| Small  | 120x160px | 72x72px     | Minimal distraction, power users |
| Medium | 180x240px | 100x100px   | Default, balanced |
| Large  | 240x320px | 140x140px   | Showcase mode, streamers |

**Overlay Visual Hierarchy (bottom-up from avatar position):**
1. **Avatar sprite** (dominant, ~60% of window) — floats directly on desktop. State-specific radial glow behind it: `rgba(168,85,247,0.15)` for thinking, `rgba(20,184,166,0.15)` for generating, none for idle, `rgba(239,68,68,0.15)` for error. Avatar has subtle drop-shadow `0 4px 12px rgba(0,0,0,0.3)` so it reads against any desktop wallpaper.

**CLI State Monitor (Rust sidecar):**

Two detection approaches to evaluate in Phase 0 spike:
- **Option A: Process-table polling** (`sysctl` / `/proc`) — detects whether Claude Code process is running or not. Maps to: idle (no process) vs. active (process exists). Cannot distinguish thinking from generating.
- **Option B: Log-file / JSONL tailing** — watches Claude Code's output log or a user-configured JSONL event stream. Maps to all four states: idle (no recent events), thinking (request sent, no tokens yet), generating (token stream active), error (error event or non-zero exit).

State mapping:
| Signal | idle | thinking | generating | error |
|--------|------|----------|------------|-------|
| No CLI process | x | | | |
| Process active, no output (>2s) | | x | | |
| Token stream active | | | x | |
| Error pattern / non-zero exit | | | | x |

Emits state events to frontend via Tauri event system. Polling interval: 200-500ms. Non-invasive: read-only observation, zero modification to CLI behavior.

**CLI Monitor Implementation:** Tokio async task spawned at app startup (not a dedicated OS thread). Uses Tauri's existing async runtime. Stores current `CliState` in `Arc<Mutex<CliState>>` as Tauri managed state. Emits `cli-state-changed` events to all windows via `app.emit()`. 200ms polling is well within tokio task scheduling precision.

**Performance notes:**
- Process-table polling (Option A): ~1-2ms per scan via `sysctl`, 5 scans/sec = ~5-10ms CPU/sec (~0.5-1%). Acceptable.
- Log-file tailing (Option B): prefer kqueue/fsnotify event-driven watching over polling. Near-zero CPU when idle, events only on file changes. Use `notify` crate.
- All overlay CSS animations use `transform` + `opacity` only (GPU-composited). Add `will-change: opacity` to the pulsing status dot.
- Sprite sheet animation: CSS `steps()` on `background-position`. Keep the sprite container as a leaf node (no children that reflow).

**App Lifecycle (tray-anchored):**
- On app startup: create management window + companion overlay window + system tray icon + CLI monitor task
- Closing management window: hides it (does not destroy). App keeps running. Companion + tray persist.
- Reopening management: tray menu "Settings" or double-click tray icon shows the management window
- Quit: only from tray menu "Quit" or Cmd+Q. Destroys all windows, stops CLI monitor, exits.
- This requires `tauri.conf.json` setting `"exitOnCloseAllWindows": false` (Tauri v2 supported) plus `close_requested` event handler to hide instead of destroy the management window.

**Degraded Mode:** When CLI detection is unavailable (Claude Code not installed, process undetectable, or running inside container/tmux), the avatar stays in idle with a subtle "monitoring inactive" indicator (dimmed status dot). User can manually trigger states via keyboard shortcuts or tray menu for demo/fun purposes.

### US-P2-001: Agent Sui 钱包 (App-Level Keypair)

### US-P2-003: Agent Behavior Engine

**验收:** companion 不再只是视觉状态切换，而是有 LLM 驱动的"意见"——看到 error 会评论，看到长时间 generating 会鼓励，idle 时偶尔说话。

**行为设计:**
```
AGENT BEHAVIOR STATE MACHINE
═══════════════════════════════
                  ┌─────────┐
    CLI event ──► │ Context │──► LLM prompt ──► reaction
                  │ Buffer  │    (if trigger   (speech bubble
                  └─────────┘     met)          + voice + glow)

TRIGGER RULES:
  idle > 30min          → "Taking a break?"
  error detected        → "Oops. Want me to look at that?" (personality)
  generating > 2min     → "This is a big one..." (encouragement)
  session start (AM)    → morning greeting with streak
  5th session today     → "Productive day!" milestone
  random (1% per min)   → idle chatter from personality pool
```

### US-P2-006: Soul Minting (本地文件 → 链上 Soul)
