# Soulidity 项目与产品工程管理手册

版本：1.0。更新日期：2026-10-06；外部资料核对：2026-10-05 至 2026-10-06。维护责任：Labs 交付统筹；专业章节由对应实施者和验收者共同维护。

本手册是 Soulidity 项目成员和执行 Agent 的必读工作规范，覆盖管理、产品、敏捷、DevOps、金融工程、DeFi 机制、Ethereum 与 Sui 合约安全，以及治理和运行。目标是让每项工作有明确用户结果、正确规则、受约束的权限和可核查证据。

本手册形成项目工作要求，不证明现有产品已经通过这些检查。Sui 是当前工程重点；Ethereum/EVM 是知识基线及涉及该链时的专项要求，不表示项目已有 Ethereum 部署。借贷、AMM、收益金库等是条件适用的金融场景，不是新增产品路线。现行架构、范围与实施状态分别见[产品架构](../docs/SOULIDITY_PROBLEM_PRODUCT_ARCHITECTURE_CN.md)、[产品版图](../docs/SOULIDITY_ECOSYSTEM_CN.md)和实际工作区的 CURRENT。

## 1 使用方式与规则边界

所有岗位首次参与项目时阅读第 1–4、9、12 节，建立共同知识基线；按任务阅读其余专业章节。后续任务引用已知版本并补读相关更新，无需反复加载全文。任务 Owner 在原 Delivery/DEV/BUG 记录中注明手册版本、适用章节、证据和剩余检查；涉及资金、权限、合约、升级或迁移时使用[评审记录模板](templates/product-engineering-review.md)。模板可内联到原卡或作为附件，不另建任务系统。

每项检查使用“通过／失败／待核验／不适用及理由”，不能把未检查填成通过，也不能把计划中的控制说成已部署。高风险变更由实施者之外的合格验收者复核；内部 AI 审查不等于外部审计。

| 层次 | 权威和用途 | 不得混用 |
| --- | --- | --- |
| 用户确认与授权 | 决定产品结果、范围和允许执行的动作 | 岗位头衔、文档和工具可用性不产生签名或资金权限 |
| 当前产品规格与工作区 | 确定要实现的行为；源码、测试、部署读回说明实际状态 | 实现与需求冲突时记录缺陷，不能用实现反过来取消已确认需求 |
| 运行规则 | [OPERATING_MODEL 第 8、9 节](OPERATING_MODEL.md)定义交付循环与 AI 执行 | 本手册不另建阶段、Owner、看板或里程碑 |
| 本手册 | 给各阶段增加适用的专业分析与证据要求 | 通用方案不能覆盖已确认产品行为，也不自动授权改造生产 |
| 历史交接与外部资料 | 解释背景、技术依据和过去结果 | 历史快照、示例代码和网页不是当前部署事实 |

保留 AC/SO 的 M1–M4、S0–S14、G1–G5、既有任务与活动 Owner。主仓库的 CURRENT 继续指向现有产品工作；管理手册更新不得接管该指针。首次应用手册发现缺口时，补入原任务或关联 Bug，不自动宣告旧产品不合格、重开全部历史任务或中止无关工作。

## 2 各领域的职责区别

| 领域 | 核心问题 | 方法 | 交付证据 |
| --- | --- | --- | --- |
| 管理职能 | 目标、资源、责任如何安排和纠偏 | 计划、组织、领导、控制 | 决策、预算、责任、偏差与纠正动作 |
| 管理科学 | 在约束和不确定性下如何选择 | 优化、排队、仿真、决策分析 | 假设、约束、比较结果、敏感性 |
| 产品管理 | 为谁解决什么问题，先做什么 | 用户研究、旅程、价值假设、路线与优先级 | 用户结果、规格、验收与实际反馈 |
| 敏捷 | 如何在不确定中小步验证 | 迭代、增量、短反馈、在制品限制 | 可用增量、评审、回顾及调整 |
| DevOps | 如何可靠交付并运行 | CI/CD、制品、配置、监控、恢复 | 构建、测试、部署身份、运行数据 |
| 金融工程 | 现金流和权利如何设计、定价、对冲和控险 | 收益模型、估值、风险度量、压力测试 | 模型说明、现金流、风险限额、验证 |
| DeFi 机制工程 | 自利参与者如何共同维持链上金融机制 | 机制设计、激励、流动性、结算、治理 | 参与者分析、经济攻击测试、清算和退出规则 |
| 智能合约安全 | 规则是否可被越权、操纵或错误执行 | 威胁建模、权限分析、不变量、审计 | 具体版本的测试、审查和部署核验 |
| 协议治理 | 谁能改变规则，权力如何约束 | 能力/角色、多签、时间锁、变更规则 | 权限图、提案、链上执行与读回 |

这些领域相互嵌套。敏捷不替代安全验证，DevOps 不决定金融价格，DAO 投票不证明经济机制安全，审计也不证明用户需要产品。下文规则属于 Soulidity 的综合实践，不宣称存在一个全行业统一的 DeFi 八步标准。

## 3 管理科学与产品决策

管理学常用的四项职能是计划、组织、领导、控制；实施贯穿其中。“管理科学”狭义上还指用定量模型辅助决策，不能仅用四项职能概括。[OpenStax 管理职能](https://openstax.org/books/introduction-business/pages/6-1-the-role-of-management)

Soulidity 的实施要求：

- 计划：明确用户结果、范围、资源、预算、依赖和验收；远期保留方向，近期细化到可执行增量。
- 组织：每个工作项有一个 Owner 和明确验收者；跨仓集成指定统一集成责任；能力、账户、签名权分别记录。
- 领导：澄清冲突、移除障碍、提供上下文和资源；允许如实报告失败，不以报表好看替代真实结果。
- 控制：对照目标检查偏差，决定修复、降风险、调整范围或停止投入；决定及理由进入原记录。

沿用 Foundation 对战略、预算和外部承诺的责任，Labs 对产品工程和交付统筹的责任。IRIS 管用户结果和计划，CIPHER 管协议设计，SABLE/LUQI/FLUX 按现有分工实施，SENTINEL 验收，HARBOR 管交付与可靠性，NOVA/ECHO 提供采用与支持反馈。角色合同见[运行规则](OPERATING_MODEL.md)，不另设未经确认的金融负责人；金融活动启用前明确具备能力的模型与风险责任人。

涉及资源取舍时记录目标、候选方案、约束和敏感假设。可用简单成本收益比较、情景树、排队分析或仿真；数据不足先写区间，不制造精确分数。优先处理阻塞整个旅程的约束；评审能力不足时减少新开工。代码量、故事点、Agent 数量不能替代价值与质量。

产品规格至少说明：用户与问题、当前可用基线、目标操作、权利与费用、正常/失败/取消/恢复状态、成功指标和非目标。所有权、访问权、素材许可、运行实例分别建模。收集外部用户证据时区分实际用户、内部试用和模拟结果。

## 4 敏捷与产品增量

敏捷重视协作、可用成果、用户参与和对变化的响应，同时保留必要的计划、文档与质量要求。[敏捷宣言](https://agilemanifesto.org/iso/zhchs/manifesto.html)

Scrum 通过目标、待办事项、Sprint 和检查调整组织增量；看板通过可视化工作和限制在制品改善流动。Soulidity 沿用现有周期和异步协调方式，不因引用 Scrum 就宣称已完整实施该框架。Sprint Review 检查产品结果，Retrospective 检查工作方式。[Scrum Guide](https://scrumguides.org/scrum-guide.html)

本项目执行约定：

1. 按完整用户结果拆分，例如“发布后在另一应用找到同一 Soul”，不要只按数据库、合约、界面分割验收。
2. Ready 要求需求明确、权威基线已知、依赖与权限可说明、验收可执行、范围能够交付。
3. Done 按原卡范围判断，并分别记录 Implemented、Verified、Released、Adopted；局部完成不能关闭父目标。
4. 新反馈进入原 backlog。紧急插入工作时明确影响和取舍，不隐性堆高并发或降低质量。
5. 缺陷记录原操作、预期/实际、环境和版本，修复后回到原操作复验；相关失败不能以无关测试数量抵消。
6. 回顾选择少量改进并指定验证方式；会议、文档和看板数量不作为敏捷效果。

## 5 DevOps 与八阶段交付

唯一主循环仍为 **Plan → Code → Build → Test → Release → Deploy → Operate → Monitor → Plan**。完整岗位、G1–G5 映射和退出条件以[运行规则第 8 节](OPERATING_MODEL.md)为准。以下列出本手册增加的专业证据，不重新定义流程。

| 阶段 | 专业检查与证据 |
| --- | --- |
| Plan | 用户结果、资金与权限影响、威胁假设、定价/风险模型适用性、变更与恢复边界 |
| Code | 规格到代码映射、权限与记账校验、版本/迁移逻辑、依赖审查 |
| Build | 固定工具与依赖、源码和制品身份、网络与配置；跨仓成对候选 |
| Test | 正常与失败路径、业务不变量、经济边界、权限反例、旧新版本和恢复 |
| Release | 确切候选、适用门禁、审计覆盖范围、残余风险、执行授权、运行责任 |
| Deploy | 同一制品到正确目标；初始化、角色/Cap 托管、地址/包/对象/交易读回 |
| Operate | 故障处理、依赖与成本、资金及业务对账、密钥和访问管理、恢复演练 |
| Monitor | 用户成功率、异常权限动作、经济风险和成本，产生原卡中的改进或 Bug |

持续集成 CI 指频繁集成并自动验证；持续交付意味着具备可发布条件；持续部署意味着通过约定检查后自动进入生产。采用 DevOps 不要求主网交易自动签名，也不等于已配置 CI/CD。

发布清单应追踪：仓库/提交及未提交差异、工具链/依赖锁、构建与配置摘要、制品哈希、环境/网络、跨仓对应版本、审查和测试结果。密钥不进入制品或日志。前端、桌面、SDK、合约、索引和内容资源分别记录兼容关系。

恢复按资源分类：Web 可以回退制品；本地数据恢复要考虑新格式；链上升级、转账和迁移不能假定可撤销。结果未知的交易先查链上状态，再决定重试，避免重复创建或付费。链上成功和内容上传成功也不能互相替代。

DORA 当前官方口径包括变更前置时间、部署频率、失败部署恢复时间、变更失败率、部署返工率。它们用于同一应用随时间改进；失败部署恢复时间不等于一切故障的恢复时间，也不能把任务 Ready 到 Done 的周期称为同一指标。[DORA 五项交付指标](https://dora.dev/guides/dora-metrics/)

结合本项目另看真实旅程成功率、首次成功用时、外部用户再次使用、支持请求、审查等待、返工及完整执行成本。先确定窗口和基线，再定 SLO 与告警阈值；不以更多部署或交易来制造优秀指标。

## 6 金融工程与 DeFi 机制

并非所有链上产品都是金融产品。Soulidity 的支付、市场、收费与分配需要资金流和精度检查；只有引入借贷、做市、抵押、收益承诺、衍生权利等机制时，才启用相应完整金融模型。游戏积分与代币区分可转让性、赎回性、发行规则和实际权利，不能因为存在积分就默认具有投资价值。

项目金融工作顺序为：定义权利与现金流 → 建模与定价 → 分析参与者激励 → 验证与压力测试 → 设定限额 → 运行监测 → 调整或退出。它与交付八阶段交叉，不建立第二条任务流水线。

| 工作 | 必须明确的内容 |
| --- | --- |
| 工具和现金流设计 | 谁付钱、谁收钱、何时结算、资产和负债币种、期限、优先级、费用与违约处理 |
| 定价 | 价格来源、报价有效期、利率/费率单位、离散计算、舍入、成本与风险补偿 |
| 激励 | 流动性提供者、借款人、清算者、套利者和治理者为何行动；补贴归零后是否仍成立 |
| 风险计量 | 市场、信用、流动性、集中度、对手方、操作、模型和依赖风险；敞口及损失承担 |
| 风险控制 | 资产准入、限额、抵押折扣、隔离、对冲、暂停和退出条件；对冲自身也有成本和风险 |
| 模型治理 | 数据、公式/代码版本、假设、校准、验证者、失效条件、变更和持续监测 |

收益披露必须分开手续费/利息等实际来源、补贴和资产价格变化；区分毛收益与费用后收益、已实现与未实现、APR 与具有明确复利假设的 APY。TVL、代币价格和交易量不能直接替代收入、偿付能力或外部采用。

适用场景的专项问题：

- 借贷：抵押估值、LTV 与清算条件、利息累计、清算奖励、市场深度、坏账归属。
- AMM/交易：报价曲线、费用、滑点、库存风险、套利、MEV、极端撤资和价格操纵。
- 金库：资产与份额换算、捐赠/首次存款攻击、策略损失、退出队列、流动性与净值时效。
- 衍生品：收益函数、保证金、标记价与结算价、资金费率、到期、违约和强平；只有相应产品才讨论 Greeks 等敏感度。
- Soulidity 收费：币种、金额、报价版本、分配对象、尾差、资格复用、失败费用、退款规则与链上实际结果一致；不自行新增退款承诺。

ERC-4626 金库的舍入及捐赠影响是份额机制风险的实例；使用标准接口不等于经济攻击自动消失。[OpenZeppelin ERC-4626](https://docs.openzeppelin.com/contracts/5.x/erc4626)

模型验证至少包含概念合理性、独立计算对照、边界与敏感性、历史/合成情景及运行结果对比；关注数据泄漏、过拟合和环境变化。金融模型风险方法可参考[美联储模型风险指导](https://www.federalreserve.gov/frrs/guidance/supervisory-guidance-on-model-risk-management.htm)，这里只借鉴验证思想，不将银行监管要求直接套用于 Soulidity。

压力场景应组合价格急跌、抵押物相关性上升、稳定币脱锚、流动性枯竭、价格源停更、Gas 上升与清算者离线；同时记录损失、偿付缺口、退出时间和恢复路径。VaR 或历史回测不能代替尾部压力测试；不得把示例参数直接作为生产阈值。[Aave 风险分类实例](https://www.aave.com/docs/resources/risks)

## 7 跨链通用的智能合约安全

每项高风险变更先定义资产、参与者、信任边界、攻击能力和损失路径，再选择验证方法。智能合约审计只覆盖明确的版本、配置和范围；语言、库、外部审计、形式化证明都不能单独保证完整产品安全。[Ethereum 合约安全](https://ethereum.org/developers/docs/smart-contracts/security/)

本项目共同检查：

| 检查 | 必须能说明的证据 |
| --- | --- |
| 业务不变量 | 资金/份额/权利怎样对应；重复结算、越权变更、无偿增发不成立的测试 |
| 权限 | 所有特权入口、实际持有人、范围、替代路径、转移/撤销条件和事件 |
| 精度 | 最小单位、缩放、中间乘除、舍入方向、零值、上限与重复小额操作 |
| 预言机 | 币种映射、精度、时效、偏差/置信度规则；源失效时各操作的安全行为 |
| 签名和请求 | 绑定链、应用、操作、资产、金额、接收方、时效和唯一性；取消及重放策略 |
| 外部依赖 | 实际地址/包、版本、配置、权限、失败模式；不只看项目名或前端常量 |
| 组合与原子性 | 多步骤和跨协议组合能否突破单步假设；跨交易部分完成如何恢复 |
| 可用性 | 无界循环、存储增长、恶意输入、锁定/争用是否阻塞关键退出和清算 |
| 隐私 | 公开链上数据、内容字节、解密策略和本地缓存分别处理；不要把可见性关键字当作加密 |

不变量要符合真实账目。例如有借贷的协议不能要求“现金余额始终不少于所有存款”，而应解释现金、应收债权、损失和负债的关系，并单独验证即时流动性。技术资源守恒也不能证明经济偿付能力。

验证组合：单元与场景测试、性质/不变量与模糊测试、差分计算、静态检查、适用的形式化验证、真实配置下的集成和恢复演练。形式化结果必须附性质、假设和覆盖边界。修复审计发现后记录重验和审计后差异；不能将旧版本审计徽章贴到任意新版本。

## 8 Ethereum 与 Sui 专项安全

### 8.1 两种执行模型的区别

| 维度 | Ethereum/EVM | Sui Move |
| --- | --- | --- |
| 主要状态模型 | 账户与合约存储、消息调用 | 对象、所有权、共享访问与能力对象 |
| 典型权限表达 | sender、owner、角色、签名授权 | Cap、对象归属、ID/类型绑定及必要的 sender 校验 |
| 组合风险 | 外部调用、回调、delegatecall、跨合约状态 | PTB 命令组合、对象关系、临时凭证和跨步骤状态 |
| 常见升级 | 代理更换实现，也存在不可升级合约 | 发布新包版本，旧包仍存在；对象迁移另行设计 |
| 关键审查 | 重入、存储布局、初始化、代币兼容、签名 | Cap 范围、对象/类型关系、abilities、版本守卫、PTB |

共同的经济、权限、预言机和运行风险仍需验证。不能把 Solidity 的检查表原样贴到 Move，也不能因 Move 的资源模型而省略经济与业务审查。

### 8.2 Ethereum 和 Solidity

以下是 EVM 工作启用时的项目检查要求，具体行为以锁定编译器、库版本和目标链规则为准：

1. 外部调用及回调：检查更新顺序、跨函数/跨合约重入和只读路径的状态一致性；CEI 与适用的重入保护配合使用，不假定转账 Gas 限制永远安全。
2. 授权与调用：不以 `tx.origin` 做业务授权；限制任意调用与 `delegatecall`；检查低级调用返回值和恶意接收者导致的拒绝服务。
3. 数值与 Gas：检查 `unchecked`、类型收窄、精度、舍入、循环上限与可能永远无法完成的批处理；不能只依赖编译器算术检查。
4. 私密与排序：链上 `private` 数据仍可观察；时间戳不能作安全随机数；交易顺序、抢跑和滑点需要产品级约束。[Solidity 安全注意事项](https://docs.soliditylang.org/en/latest/security-considerations.html)

5. 代币适配：明确支持哪些资产行为；针对不标准返回值、手续费转账、rebase、回调、冻结和小数位设计测试。不能只因使用安全转账包装，就假定实际到账等于请求金额。
6. 离线签名：检查 EIP-712 域、chainId、验证合约、nonce、截止时间、签名者和操作内容；按支持范围验证合约钱包。EIP-712 本身不提供重放防护。[EIP-712](https://eips.ethereum.org/EIPS/eip-712)
7. 代理识别：明确 Transparent、UUPS 或 Beacon 及各自实际升级入口；核验 admin、implementation 和 beacon。UUPS 的升级授权位于实现逻辑，不能只检查 ProxyAdmin。[OpenZeppelin Proxy](https://docs.openzeppelin.com/contracts/5.x/api/proxy)、[ERC-1967](https://eips.ethereum.org/EIPS/eip-1967)
8. 初始化与存储：部署时保护代理初始化，限制再初始化；实现合约按设计锁定初始化器。升级前比较存储布局、继承和初始化顺序，并验证已有状态；不要通过跳过兼容检查来掩盖差异。[Upgradeable Contracts](https://docs.openzeppelin.com/upgrades-plugins/writing-upgradeable)

发布读回必须覆盖实际代理与实现，而非只验证一个源码页面。放弃一个 `owner` 不证明所有升级或管理入口消失；是否永久不可升级须按实际代理机制验证。涉及 L2 时额外说明排序器故障、最终性、桥与退出依赖，不能直接套主网假设。

### 8.3 Sui Move

以下是 Sui 工作的项目检查要求：

1. 权限与对象：核对 Cap 和被管理对象的对应关系、对象 ID、动态字段键、资产类型及归属；合法类型的错误实例也可能越权。共享对象仍必须经函数校验才能改变。[Sui 安全实践](https://docs.sui.io/develop/security/best-practices)
2. abilities 与入口：逐项解释 `copy/drop/store/key` 是否必要；允许复制、丢弃、存储或公开转移是否符合业务。`entry` 不是管理员权限，前端隐藏按钮也不构成访问控制。[Sui Move 概念](https://docs.sui.io/develop/write-move/sui-move-concepts)
3. 金额与记账：检查 `Coin<T>`、余额、份额、欠款和资格的区别；整数溢出会 abort，不代表舍入、公式或可用性正确。奖励累计、利息和报价都需边界测试。
4. PTB：将公开可组合操作按恶意顺序测试。hot potato 临时凭证应只能由完成业务义务的路径消耗，不能意外复制、丢弃或存储；记录它绑定的池、币种、金额与用途。成功/失败的交易原子性不替代跨交易恢复和 Gas 成本处理。[Sui PTB](https://docs.sui.io/develop/transactions/ptbs/prog-txn-blocks)
5. 时间：需要接近实时时使用合适的 `Clock`；epoch 开始时间不能替代准确的截止时间。测试到期前、等于到期、到期后与同一交易中的边界。[Sui 链上时间](https://docs.sui.io/sui-stack/on-chain-primitives/access-time)
6. 随机：使用适用的链上随机机制，检查可组合性限制、选择性 abort、不同结果的 Gas 路径；不用对象 ID、时间戳或客户端自报随机数决定有价值结果。[Sui Onchain Randomness](https://docs.sui.io/sui-stack/on-chain-primitives/randomness-onchain)
7. 资产控制：登记 `TreasuryCap<T>` 的铸造/销毁路径；受监管币检查 `DenyCapV2<T>` 的地址限制及是否允许全局暂停。币种冻结权限与协议暂停权分开。[Sui Coin](https://docs.sui.io/references/framework/sui_sui/coin)
8. 依赖与运行：核对链、包版本、对象和 SDK 配置；监控共享对象争用、交易失败、索引延迟和执行机器人。余额已花费、请求超时与交易失败不是同一状态。

### 8.4 Sui 版本与迁移

Sui 升级发布新的包版本，旧包不会被删除；`init` 不会因升级重跑。依赖包升级也不会自动将本包指向新版本。因而升级要同时设计新代码、对象状态、旧入口、调用方和依赖关系。[Sui 包升级](https://docs.sui.io/develop/publish-upgrade-packages/upgrade)

本项目要求：

- 对需要版本控制的共享状态，从初版设计守卫；所有相关入口检查版本，不能只保护迁移函数。
- 迁移验证授权、起止版本、重复执行、资产和权利保持；验证升级完成但迁移未完成的状态。
- 旧版本是否仍可访问当前资产必须实测。前端换包 ID 不能阻止用户直接调用旧包。
- 固定旧/新包、依赖、升级内容摘要、Cap 与状态对象，更新 SDK 和运行端；测试已存在对象，而非只新建样本。
- 不假设可还原旧代码就能还原已改变状态；预先说明修复、继续迁移、暂停或退出边界。

## 9 权限治理与各种锁

### 9.1 权限清单

每项权限记录实际控制对象/地址、持有人、允许动作、金额/范围/频率限制、授权与撤销路径、时间约束、紧急例外、事件和监控人。

必查权力包括升级、调参、资金转移、增发/销毁、资产准入、价格源替换、暂停/恢复、迁移、权限再授予，以及外部依赖的管理权。审查可达路径，不能只看一个 `owner`、一个 Cap 或角色名称。

区分提案人、批准者、执行者、取消者和紧急处置者。多签记录实际阈值、密钥独立性和失联恢复；同一人控制多把钥匙不产生真正独立判断。被攻陷密钥处置应包括角色/Cap 迁移、未执行提案、前端与签名入口及对账。

### 9.2 锁的分类

| 控制 | 限制什么 | 必须验证的边界 |
| --- | --- | --- |
| 多签 | 单人作出特权决定 | 不自带等待期，存在共谋和失联风险 |
| 升级时间锁 | 代码变更的执行时间 | 不能被直接升级、另取 Cap 或替换治理绕过 |
| 参数时间锁 | 关键配置修改时间 | 所有等效修改入口和缩短延迟的动作受约束 |
| 升级策略收紧 | 允许改变的代码范围 | 兼容性、权限安全、经济安全分别验证 |
| 永久放弃升级 | 沿既有机制修改代码的权力 | 不自动取消原有调参、增发、提取和暂停权 |
| 代币归属期/锁仓 | 指定资产的提前释放 | 锁仓合约自身升级、取消、转让和应急路径 |
| 流动性锁 | 指定 LP 凭证或头寸撤出 | 不保证价格、偿付、手续费政策或其他 LP 不撤资 |
| 提现冷却/队列 | 用户赎回节奏 | 退出时间、资源不足、优先级及取消规则 |
| 熔断/暂停 | 异常时停止指定动作 | 明确覆盖范围、恢复权及正常退出是否可用 |
| 防重入/状态锁 | 调用或状态转换中的重复执行 | 不替代权限、金额和经济模型验证 |
| Sui 对象交易锁定 | 对象交易协调 | 不是投资者保护或治理时间锁 |

### 9.3 升级策略与时间锁

Sui 以 `UpgradeCap` 管升级。内置策略从 Compatible、Additive、Dependency-only 到不可升级逐步收紧：Compatible 可修改实现但保持规定兼容性；Additive 限制原代码变更并允许新增及依赖变化；Dependency-only 仅允许依赖变化。策略不能放宽；`make_immutable` 消耗升级能力且不可逆。[Sui Package API](https://docs.sui.io/references/framework/sui_sui/package)

多签和延迟不是 Sui 包发布后自动具有的属性，要检查自定义策略如何控制 Cap。策略应约束具体升级内容；考虑将策略置于独立、不可升级的包，避免被其管理的代码改变保护规则。[Sui 自定义升级策略](https://docs.sui.io/develop/publish-upgrade-packages/custom-policies)

EVM 可通过角色管理和 TimelockController 等机制延迟管理操作；提案、执行、取消与管理员角色须分别检查。时间锁自管理也有失去必要执行者后永久锁死的可用性风险。[OpenZeppelin Access Control](https://docs.openzeppelin.com/contracts/5.x/access-control)

Soulidity 评审时间锁时必须验证：

1. 提案绑定确切目标、网络、操作、参数、金额、代码/依赖摘要和必要的执行前置条件。
2. 等待开始、允许执行、取消、过期或永不过期的语义明确；未到期和重复执行失败。
3. 等待期间不能替换载荷；不允许通过缩短延迟、换角色、直接控制底层 Cap/代理形成隐蔽绕路。
4. 紧急例外的范围和控制者公开；紧急角色若能任意升级，必须披露实际信任边界，不能称所有升级都受延迟保护。
5. 用户能了解变更且有实际可行的响应/退出路径；锁仓周期与赎回排队不能使等待期失去意义。
6. 多签失联、执行失败和治理模块故障有明确处置边界；不为“可恢复”留未披露万能后门。

升级性与不可升级性各有代价：前者引入治理信任，后者限制修复。根据产品生命周期、资金暴露和退出能力选择，不机械要求所有包永久不可升级。执行不可逆放弃升级必须属于已明确授权的实际动作，本手册不代为授权。

## 10 运行风险与故障处置

| 场景 | 处置设计与验证 |
| --- | --- |
| 价格停更或异常 | 按操作区分限制新增风险、还款、补抵押、清算和提现；不能盲用错误价格 |
| 抵押物暴跌或流动性枯竭 | 检查实际成交深度、清算能力、限额和坏账分配；不得掩盖缺口 |
| 依赖协议/桥/资产发行方故障 | 识别直接与间接敞口、冻结能力、替代路径和退出条件 |
| 权限异常 | 检查事件、Cap/角色持有人和未执行提案，按既有授权隔离受影响动作 |
| 交易结果未知 | 保存原请求与交易标识，查询执行效果，再选择恢复或重试 |
| 前端与供应链受损 | 核查域名、构建制品、依赖、交易载荷及收款对象；停止分发受损版本 |
| Walrus/Seal/索引异常 | 分别检查内容可用期、完整性、访问策略、密钥服务和索引新鲜度 |

故障闭环：识别影响 → 指定处置责任 → 在授权内限制损失 → 保存必要证据 → 修复/迁移/退出 → 对账及原操作复验 → 告知受影响方 → 复盘回原 backlog。外发仍按具体授权执行，不把手册作为自动广播指令。

暂停按最小必要范围设计。停止新增借款而保留还款是可选模式，不能机械适用于所有故障；错误价格下继续清算同样可能损害用户。恢复前验证原因已处理、资金/权利对账和用户操作，而非仅观察告警消失。

监控至少覆盖真实用户结果、交易失败与延迟、异常管理操作、资金/份额变化、价格源时效和适用经济限额。每条关键告警有数据源、窗口、阈值依据、响应者和演练结果；没有真实验证就标“待建立”。

## 11 Soulidity 的具体应用

当前确认架构以链上业务规则、Walrus 内容、Seal 条件访问及客户端/运行端计算协作；AC/SO 不因此新增自有业务后端。下表是验收要求，不是完成声明。

| 用户结果 | 跨领域必须共同检查 |
| --- | --- |
| 上传并发布 Maker | 规格与内容版本、存储期限、费用、授权、钱包取消、上传成功但链上未完成时恢复 |
| Complete 后产生 Soul | 对象与来源绑定、唯一操作结果、分账精度、请求超时先查询、重复点击/重开恢复 |
| 在 SO 使用同一个 Soul | 跨仓候选匹配、链/包/对象身份、内容完整性、索引延迟和可理解的等待状态 |
| Paid Access 或授权 | 支付所得权利、期限、持有人轮次、范围、撤销/过期与解密行为一致 |
| 转让和装备 | 所有权与使用权区分、旧授权失效、装备包含范围、不能用错误实例操作其他 Soul |
| 游戏和 Agent 运行 | 教学与真实结算分离、随机性、凭证来源、重复领奖、支出预算和停止条件 |

Seal 控制获准解密，不保证接收者已经获得的明文能够被收回；Walrus 的保存与续期需要实际管理；链上持有关系也不自动解决素材许可或原创争议。这些边界在用户流程中清楚表达，具体许可和适用义务由相应责任人核定。

对这条真实旅程使用管理职能确定责任与资源，敏捷选择下一块可验收增量，DevOps 管成对构建和运行证据，金融分析核对实际收费和分配，合约安全验证对象及权限，治理规范约束后续修改。没有借贷或金库的部分可明确记金融专项不适用。

## 12 实际工作记录与完成判断

沿用[AI 任务合同](templates/ai-work-item.json)与原卡。轻量改动记录适用性和相关检查即可；高风险工作附[产品工程评审记录](templates/product-engineering-review.md)。材料可以是原规格、已有测试或发布清单的链接，不要求重复抄写。

| 必要材料 | 内容 | 实际责任 |
| --- | --- | --- |
| 产品与范围 | 用户结果、验收、权利和费用、非目标 | 原产品 Owner 与 IRIS |
| 机制与模型 | 资金/权利流、假设、定价与压力情景 | 对应设计者；适用时明确金融责任人 |
| 威胁与权限 | 资产、攻击面、Cap/角色、升级和锁 | CIPHER 与原实现 Owner |
| 验证与放行 | 确切候选、失败/剩余项、独立复核 | SENTINEL 与已有放行责任人 |
| 运行与退出 | 监控、应急、对账、迁移/退出边界 | HARBOR 与对应运行 Owner |

适用检查失败时，只阻止依赖该条件的放行，继续无关的已授权工作。无法确认权限或资金影响时，不执行受影响的不可逆动作；先完成可读回、可评审的候选与证据，沿既有决策路径处理。不得为赶进度修改测试使之迁就错误行为，也不得把“接受风险”当作已修复。

任务关闭前回答：原用户结果是否达成；证据对应哪个候选与环境；适用风险是否验证；谁承担剩余工作；上线后由谁观测。线上 Bug 必须在原操作复验；纯文档任务不需要伪造生产验收或触发全量产品测试。

手册维护在专业知识、架构或工具版本实质变化时进行：核对官方依据、审阅差异、更新版本和适用任务。Owner 在下一次推进任务时补读变化；不批量宣告现有任务已符合新规范。与现行产品确认冲突的候选设计，应先显式记录并解决冲突。

本版已核对的技术资料链接见各节。外部文档的 `latest` 与库主版本可能变化；每次实际发布仍需固定项目使用版本、依赖与目标链，不能将本手册日期当成未来版本的安全保证。
